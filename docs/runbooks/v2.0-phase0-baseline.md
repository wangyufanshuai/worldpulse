# V2.0 Phase 0 baseline runbook

This runbook records the engineering baseline before the first V2 module
migration. It is not a V1.12 release approval and it does not approve the
historical Pilot corpus.

## Baseline scope

- Git baseline: `8e4b20d`
- Application version: `1.12.0-dev`
- API contract: `v11`
- Historical Pilot: 24 Evidence reviews pending, 12 Case reviews pending
- V1.12 release track: frozen and separate from V2 code work

## Required local checks

```powershell
python -m compileall -q app
python scripts/verify_v2_boundaries.py
python -m pytest -q
npm --prefix frontend run test:unit
npm --prefix frontend run build
npm --prefix frontend run test:e2e
python -m app.manage migrate verify
python scripts/verify_release_artifacts.py
npm --registry=https://registry.npmjs.org --prefix frontend audit --audit-level=high
git diff --check
```

The backend and browser checks are intentionally separate: a green SQLite
run does not prove PostgreSQL concurrency, and a green unit suite does not
prove browser lifecycle cleanup. The five non-live skips in the backend
snapshot have a fixed accounting: four `postgres_live` integration tests
(covered by the CI PostgreSQL service) and one `evaluation_full` release gate
(covered only when the externally curated corpus and sealed labels are
provisioned).

## Current recorded evidence

The V2 Phase 0 checkpoint verification is:

- Backend in isolated CPython 3.11 lock environment: `234 passed, 5 skipped`
- Frontend unit: `61 passed`

- Frontend type check: passed
- Production build: passed
- Migration verification: `10 migrations, 83 tables, status ok`
- Artifact scan: passed
- npm high-severity audit: `0 vulnerabilities`
- Python runtime and development lock audit: `No known vulnerabilities found`

The local command above is the SQLite/full-suite baseline. CI's
`Live PostgreSQL migration and concurrency gates` step applies the numbered
migrations and executes both `tests/test_postgres_integration_v16.py` and
`tests/test_postgres_scenario_compiler_v19.py` against PostgreSQL 16. Those
four tests are the only PostgreSQL portion of the five-skip accounting.

The V1.12 `evaluation_full` release evaluator is separate. It is not proven by
the local SQLite suite or by CI PostgreSQL. Run it only through the manual
`.github/workflows/evaluation_full.yml` workflow on a dedicated,
provisioned runner. The runner must provide the approved 120-case corpus,
content-addressed evidence blobs, an active 30-case sealed label pack, and the
corresponding `WORLDPULSE_BLIND_LABEL_KEYS` environment secret. Dispatching
with a missing corpus, database, pack, or decryption key fails closed; no
empty fixture or pytest skip is accepted as a release result. See
`docs/runbooks/v1.12-evaluation-release.md` for the curation and review
procedure.

## Phase 0 exit criteria

1. `v2.0-architecture-program.md`, ADR-0001 and the boundary manifest are
   present and reviewed by the implementation agent.
2. `verify_v2_boundaries.py` passes with zero forbidden imports.
3. Frontend lockfile and high-severity npm audit pass.
4. `requirements.lock` installs and passes the full suite in an isolated
   CPython 3.11 environment; the global developer environment is not accepted
   as the reproducibility proof.
5. The full non-live regression suite remains green.
6. A local, reversible checkpoint exists; no remote push or release Tag is
   created.
